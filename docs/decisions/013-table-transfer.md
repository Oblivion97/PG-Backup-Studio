# 013 — Table transfer: copy one table's rows into another database

_Date: 2026-11-17 · Status: **approved by the user 2026-11-17** after trying it; released in v0.12.0 ("select a table to
transfer to a new db that is connected to studio; if the schema matches exactly suggest direct transfer, if not the
user gives a schema, the app asks to map the columns, then confirm the transfer")._

1. **Per-server Transfer tab** (`#/s/<id>/transfer`) between Query and Admin. The source is a table, view,
   materialized view or foreign table on this server; the target is any saved server (the same one included), any
   database, any schema, an existing table or a new name.
2. **Compare first.** `POST …/transfer/compare` reads both catalogs and answers one of:
   - `identical`: same column names with the same types (order does not matter) and the same generated columns →
     "direct transfer", every column mapped by name.
   - `different` → a mapping table: one row per target column, a source column picked for it (same name, then
     case-insensitive name, suggested), or left empty (the column's default / NULL). Badges: same type, converted,
     check type (different type category), required (NOT NULL without default and nothing mapped: start is blocked).
     Generated target columns cannot be filled.
   - `missing` → the table (and the schema, if needed) is created from the source: columns, types, NOT NULLs,
     defaults, primary key. Serial columns become `GENERATED BY DEFAULT AS IDENTITY` (the source's sequence does not
     exist there); identity and generated columns are kept. Other indexes, foreign keys, triggers, grants are not
     copied. The CREATE statements are shown before anything runs.
3. **Rows already in the target**: *add* (plain COPY; a duplicate key stops the transfer), *skip existing* (COPY into
   a temp table, then `INSERT … ON CONFLICT DO NOTHING`; needs a primary key or unique constraint) or *delete first*
   (`TRUNCATE`, the table name must be typed).
4. **How the rows travel**: `COPY (SELECT <mapped source columns> FROM t [WHERE filter]) TO STDOUT` on the source,
   streamed through the app into `COPY target (<mapped columns>) FROM STDIN`. Text format, so every value is converted
   by the target column's type exactly as typed input would be; a value that cannot be read stops the transfer with
   the row and column named. No size limit, nothing held in memory beyond a chunk.
5. **Safety**: the source runs READ ONLY + REPEATABLE READ (one snapshot; the optional row filter cannot write — it
   is checked with EXPLAIN in the review). Everything on the target — create, truncate, copy, insert, sequences — is
   **one transaction**: an error or a cancel rolls it all back ("Nothing was changed in the target"). Lock timeout
   15 s on both sides. Sequences of mapped serial / identity columns are moved forward past the copied values (never
   backwards); if that is not allowed it is a warning, not a failure.
6. **Review before start**: `POST …/transfer/preview` validates everything and returns the exact SQL (source and
   target), the row estimate and warnings; the confirm dialog shows it. Start is `POST …/transfer` → a job
   (`kind: "transfer"`) in Activity with progress (rows / estimate), cancel, log; and a History entry (source,
   target table, rows written / skipped). The job marks both the source and the target database busy, so they cannot
   be dropped or renamed meanwhile.
7. **A query as the source** (user request, same day: "I query a db with multiple tables, then transfer the result
   into another db table"). The source card switches between *A table* and *A query*. The query (SELECT, WITH …
   SELECT, VALUES, TABLE; trailing semicolons dropped) is wrapped as `SELECT <mapped columns> FROM (<query>) AS pgbs_q`
   (on their own lines, so a trailing `--` comment is harmless), so a second statement is a syntax error and nothing runs; it still runs READ ONLY. Its result columns
   (name and type from the result description, `format_type`) take the place of the table's columns: compare, mapping
   and create-table work the same (a created table has no primary key). Duplicate or unnamed result columns are
   refused with "name them with AS". In the SQL workspace a result has a **Transfer rows…** button that opens the
   Transfer tab with that statement and database filled in.
8. Code: `engine/transfer.py`, `JobManager.start_transfer`, `static/transfer.js` (the tab and the Activity / History
   pieces for transfers). Tests: `tests/test_transfer.py` (needs PostgreSQL).
